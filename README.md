# TenderCheck — тренажёр банковского аналитика

Образовательная браузерная игра для студентов СПО и вузов, изучающих **банковское дело**
(специальность 38.02.07 «Банковское дело» и смежные направления). Игрок — аналитик банка: он оценивает
кредитные и тендерные заявки компаний, ищет красные флаги в финансовых показателях и принимает решение —
**одобрить**, **отклонить** или **отправить на доработку**.

Адрес проекта: **https://tendercheck.pro** (статический сайт, без бэкенда и внешних запросов).

## Возможности

- **24 заявки** (по 8 на уровень) из 17 отраслей: кредиты и банковские гарантии для тендеров.
- **Три уровня:** Стажёр, Аналитик, Начальник отдела. На каждом свой таймер на заявку и лимит ошибок.
- **Карточка заявки:** компания, отрасль, сумма, срок, цель и шесть показателей — текущая ликвидность,
  Долг/EBITDA, рентабельность продаж, кредитная история (рейтинг A–D), обеспечение, опыт в тендерах.
- **Решение + обоснование:** три кнопки и необязательное текстовое поле.
- **Разбор после каждой заявки:** оценка каждого показателя (норма / внимание / красный флаг), эталонное решение
  и объяснение, почему оно верное.
- **Итоги:** очки, точность, время, таблица ответов, разбор ошибок, кнопка «Играть снова».
- **Глоссарий** — 21 статья с поиском. **«О проекте»** — описание, правила, управление.
- **Прогресс в localStorage:** открытые уровни, лучший результат на каждом уровне, статистика. Тема (тёмная по умолчанию) запоминается.
- **Адаптивная вёрстка** для десктопа и смартфона, управление с клавиатуры (1, 2, 3, Enter, Ctrl+Enter).

### Правила начисления очков

| Ситуация | Очки |
|---|---|
| Решение совпало с эталоном | 100 + до 30 за скорость (пропорционально оставшемуся времени) |
| Допустимое решение (частичный балл, не ошибка) | 40 |
| Неверное решение или время вышло | 0 и +1 к счётчику ошибок |
| Содержательное обоснование (≥ 25 символов, названы значимые показатели) | +20 при верном или допустимом решении |
| Множитель уровня | Стажёр ×1, Аналитик ×1,25, Начальник отдела ×1,5 |

| Уровень | Время на заявку | Лимит ошибок |
|---|---|---|
| Стажёр | 90 с | 4 |
| Аналитик | 60 с | 3 |
| Начальник отдела | 45 с | 2 |

Игра на уровне завершается досрочно, когда число ошибок достигает лимита. Следующий уровень открывается, когда
предыдущий пройден: рассмотрены все 8 заявок и лимит ошибок не исчерпан.

## Технологический стек и принятые решения

| Что | Выбор |
|---|---|
| Язык и платформа | Kotlin Multiplatform 2.0.21, цель **Kotlin/JS (IR)** |
| Интерфейс | **kotlinx-html** (DOM-билдер) + собственный CSS |
| Данные | `kotlinx-serialization-json` 1.7.3 |
| Тесты | `kotlin.test`, запуск в Node.js |
| Сборка | Gradle 8.10.2 (Kotlin DSL), JDK 17+ |

### Почему Kotlin/JS + kotlinx-html, а не Compose Multiplatform (Wasm)

Задание называет Compose Multiplatform for Web (Wasm) приоритетным вариантом, а Kotlin/JS + kotlinx-html —
допустимым запасным. Выбран запасной по следующим причинам:

1. **Проверяемость сборки.** Compose/Wasm тянет тяжёлую цепочку (Wasm-таргет, Skiko, много транзитивных
   зависимостей) и требует браузеров с WasmGC. Автор готовил проект в окружении без доступа к Maven Central
   и не мог убедиться, что такая сборка проходит. Стек Kotlin/JS + kotlinx-html состоит из официальных стабильных
   библиотек JetBrains и минимален по зависимостям.
2. **Тип приложения.** Игра — это формы, таблицы и много текста. Для такого интерфейса DOM подходит лучше
   канваса Compose: нативные `textarea` и поле поиска, выделение и копирование текста, доступность для
   экранных читалок, адаптивность на CSS.
3. **Лёгкость и совместимость.** Бандл небольшой, работает в любом современном браузере, в том числе на
   слабых учебных компьютерах и смартфонах.

### Архитектура

```
commonMain  — не зависит от браузера и DOM
  model/    модели: Scenario, Decision, Difficulty, Metric, Severity …
  engine/   RiskAnalyzer (красные флаги), ScoringEngine (оценка и очки), GameSession (партия)
  storage/  Progress и ProgressRepository поверх интерфейса KeyValueStore
  data/     ScenarioRepository (заявки) и Glossary (глоссарий)
  util/     форматирование чисел, сумм и времени без зависимостей от платформы
jsMain      — только то, что обращается к браузеру
  ui/       App (состояние и обработчики), Shell.kt и Game.kt (отрисовка экранов)
  storage/  LocalStorageStore — реализация KeyValueStore на localStorage
  resources index.html, styles.css, favicon.svg, CNAME, _headers
commonTest  — тесты логики
```

Слой интерфейса находится в `jsMain`, а не в `commonMain`: DOM-API платформенно-зависим, а вся логика игры
остаётся общей и тестируется без браузера. Все знания о «красных флагах» собраны в `RiskAnalyzer`
(пороги — в `RiskThresholds`), а подсчёт очков — в `ScoringEngine`, который не зависит ни от UI, ни от часов:
затраченное время передаётся параметром.

### Как заявки попадают в игру

Единый источник — человекочитаемый файл **`data/scenarios.json`**. Gradle-задача `generateScenarios`
встраивает его в Kotlin-константу при сборке, поэтому игра работает офлайн, даже если открыть `index.html`
без веб-сервера, и не делает ни одного сетевого запроса. Чтобы добавить заявки, достаточно дописать объекты
в JSON и пересобрать проект.

Формат заявки:

```json
{
  "id": "L1-01",                       // уникальный идентификатор
  "level": "INTERN",                   // INTERN | ANALYST | HEAD
  "kind": "CREDIT",                    // CREDIT | TENDER (банковская гарантия для тендера)
  "company": "ООО «Название»",
  "industry": "Отрасль",
  "about": "Краткое описание компании",
  "amountMln": 40,                     // сумма запроса, млн руб.
  "termMonths": 36,
  "purpose": "Цель кредита или гарантии",
  "currentRatio": 2.1,                 // текущая ликвидность
  "debtToEbitda": 1.8,                 // null, если EBITDA ≤ 0
  "salesMarginPct": 9.5,               // рентабельность продаж, %
  "creditRating": "A",                 // A | B | C | D
  "collateral": "PLEDGE",              // PLEDGE | GUARANTEE | NONE
  "tenderContracts": 6,                // исполнено контрактов
  "correct": "APPROVE",                // APPROVE | REVISE | REJECT
  "acceptable": ["REVISE"],            // допустимые решения (частичный балл), можно []
  "explanation": "Разбор: почему верно именно это решение"
}
```

Требования: не использовать в тексте символы `$` и `"""`, кавычки в названиях — «ёлочки». Тест `ContentTest`
проверяет, что на каждом уровне ровно 8 заявок, идентификаторы уникальны, а эталонные решения согласованы
с красными флагами:

- «одобрить» — нет красных флагов и не более двух предупреждений;
- «отклонить» — не менее двух красных флагов;
- «на доработку» — не более одного красного флага и хотя бы одно замечание.

## Сборка и запуск

Нужны **JDK 17+** и интернет при первой сборке (Gradle скачает Kotlin, Node.js и Yarn).

```bash
# Полная сборка: тесты + продакшен-бандл + копирование в ./dist
./scripts/build.sh

# Локальный запуск готового сайта
cd dist && python3 -m http.server 8080      # откройте http://localhost:8080

# Режим разработки с автоперезагрузкой
./gradlew jsBrowserDevelopmentRun

# Только тесты
./gradlew allTests
```

Результат сборки: `build/dist/js/productionExecutable/` (копия — в `dist/`). Это обычная статическая папка,
которую можно положить на GitHub Pages, Netlify, Vercel или Cloudflare Pages.

После первой сборки появится файл `kotlin-js-store/yarn.lock` — добавьте его в репозиторий, чтобы сборки
были воспроизводимыми.

## Тесты

`src/commonTest` содержит 42 модульных теста логики и проверки контента:

- `ScoringEngineTest` — вердикты, очки, бонусы за скорость и обоснование, множители уровней;
- `RiskAnalyzerTest` — пороги и красные флаги на границах значений;
- `GameSessionTest` — очередь заявок, лимит ошибок, итоги и точность;
- `ProgressRepositoryTest` — сохранение прогресса, открытие уровней, лучший результат, повреждённые данные;
- `ContentTest` — 24 заявки, согласованность эталонов, глоссарий не короче 15 статей;
- `FormatTest` — форматирование чисел, сумм, времени и склонений.

## Что проверено при подготовке

Проект подготовлен в окружении без доступа к Maven Central, поэтому реальная Gradle-сборка Kotlin/JS и работа
интерфейса в браузере **не проверялись**. Что проверено:

- логика (`model`, `engine`, `util`, `data/Glossary`) скомпилирована компилятором Kotlin 2.0.21 на JVM;
  29 из 42 тестов (`ScoringEngineTest`, `RiskAnalyzerTest`, `GameSessionTest`, `FormatTest`) выполнены и пройдены;
- реальный `RiskAnalyzer` прогнан по всем 24 заявкам из `data/scenarios.json`: эталонные решения согласованы
  с красными флагами (то же проверяет `ContentTest`);
- остальной общий код (`ProgressRepository`, `ScenarioRepository`) прошёл проверку типов; единственное, что компилятору
  в этом окружении было недоступно, — методы `serializer()`, которые генерирует плагин сериализации.

Не запускались: оставшиеся 13 тестов (`ProgressRepositoryTest`, `ContentTest`), компиляция `jsMain`
(интерфейс на kotlinx-html) и итоговый бандл. Если при первой сборке Gradle сообщит об ошибке — пришлите её текст, и она будет исправлена.
